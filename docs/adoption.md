# Adoption plan

The goal is at least 20 organic GitHub stars. It is a target, not a result or
promise. The GitHub repository is public, but meaningful independent research-user adoption\nhas not been verified. Stars, installs and downloads are not peer validation.

## Give a new user a useful first run

- Keep the synthetic demo under three minutes and runnable without API keys.
- Lead the README with the split-boundary problem and the evidence workflow.
- Include a small dataset, offline report export, and a repair plan users can inspect.
- Show measured benchmark results with explicit limits rather than broad accuracy claims.

## After a scientifically reviewed release

1. Confirm the current-head GitHub CI, including controlled benchmark checks,\n   passes; obtain user approval before profile changes.
2. Record an actual 45–60 second demo: load records, inspect a component, review
   removal IDs, retain the test split, and re-audit the repaired data.
3. Publish the drafted LinkedIn post and X thread after replacing the repository
   URL. Submit a concise Show HN when the public demo and installation work.
4. Share in a relevant practitioner discussion only where project sharing is
   permitted and the project answers the question. Do not mass-post or ask for
   stars from people who have not used the tool.
5. Ask early users for a small redacted case the detector missed. Prioritize
   installation failures, confusing evidence, and inappropriate grouping first.
6. Report views, clones, completed demo runs reported by volunteers, meaningful
   issues, contributors, and stars after one and two weeks. No tracking is built
   into the application.

## First contributions worth accepting

- A minimal regression dataset with a clearly labeled overlap.
- A normalization edge case and its expected behavior.
- A documented group-definition example from a new domain.
- Keyboard accessibility and real-browser layout checks.

No launch posts, submissions, or messages have been sent by this project setup.
